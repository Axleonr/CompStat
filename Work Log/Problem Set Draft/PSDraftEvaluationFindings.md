### Findings — Module 1

**E-M1-1 (M) — PS1.6 specifies one experiment and verifies a different one.** The Statement tells the student to "repeat until you have accumulated at least **500** accepted draws" — a stopping-rule (negative-binomial) design in which acceptances are fixed and attempts are random. The Verification tells the same student that "at **20,000,000** naive attempts your empirical rate should fall within 3.167×10⁻⁵ ± 3.78×10⁻⁶" — a fixed-attempt design in which attempts are fixed and acceptances are random. The two cannot both be executed. Everything downstream follows the ref implementation's design, not the statement's: `ps1_6_ref.py` fixes `N_NAIVE = 20_000_000`; the log records "667 accepted", a count impossible under a procedure that stops at 500; the discussion note says the naive method wastes "nearly all of its **20 million** draws" (under the stated procedure the expected attempt count is ≈**15.7 million**, evaluator-simulated). The band's provenance confirms the diagnosis: ±3.78×10⁻⁶ is exactly 3× the Bernoulli SE at fixed n = 20,000,000 (recomputed: 3.775×10⁻⁶). *Mitigating measurement (evaluator):* the band is conservative for the stopping-rule design — 0 of 200 simulated student runs fell outside it — so this is a specification defect, not a wrong number. *Evidence:* draft PS1.6 Statement (Naive method), Verification tier-3 bullet, Discussion note; `ps1_6_ref.py` (`N_NAIVE`, `naive_empirical(seed, n_attempts)`); `ValidationLog_0_10.md` PS1.6 entry. *Suggested disposition (owner's call, not applied):* align the statement to the validated design, or re-derive and re-log the band for the stopping-rule design.

### Findings — Module 3

**E-M3-1 (M) — PS3.3's BC_a α-level convention is internally inconsistent; a literal implementation builds a 90% interval and fails the problem's own sanity check.** The printed formula uses z^(α) and z^(1−α), with "z^(α) = Φ⁻¹(α)" defined explicitly two lines below. The sanity check then says: "if you artificially force â = ẑ₀ = 0, the formula above must reduce *exactly* to the percentile method's **α₁ = α/2, α₂ = 1 − α/2** (E&T Eq. 14.11)." Setting â = ẑ₀ = 0 in the printed formula gives α₁ = Φ(z^(α)) = **α** and α₂ = **1 − α** — not α/2 and 1 − α/2, under any reading of α. The problem elsewhere fixes 95% intervals read at "the 2.5th and 97.5th percentiles", i.e. α = 0.05, so a student implementing the formula as written obtains (0.05, 0.95): a **90%** BC_a interval that then fails the sanity check it is told to trust. The reference implementation uses the other convention — `ps3_3_ref.py`: `Z_ALPHA_LO = stats.norm.ppf(ALPHA / 2)  # z^(0.025)`, `Z_ALPHA_HI = stats.norm.ppf(1 - ALPHA / 2)` — and the 07/15 log entry accordingly reports the reduction as "α1 = 0.02500, α2 = 0.97500". The cause is visible: E&T's Ch. 14 formulas are written for a **1 − 2α** interval (α = 0.025 for 95%); the draft imported the formula but not the convention, and the draft's own α is the 0.05 one. This lands on the single place in the module where the student is told to validate their implementation against the source. *Evidence:* draft PS3.3 Statement, BC_a block (formula, the z^(α) = Φ⁻¹(α) definition, the "Sanity check before trusting your BC_a code" paragraph) and Verification tier-1 E&T bullet; `ps3_3_ref.py` lines 36–37 and `bca_alpha_endpoints`/`alpha_transform`; `ValidationLog_0_10.md` PS3.3 (07/15/2026) "SANITY CHECK" clause. *Suggested disposition (owner's call, not applied):* state the convention explicitly (either write z^(α/2)/z^(1−α/2) in the formula, or say α = 0.025 for a 95% interval and fix the reduction sentence to α₁ = α, α₂ = 1 − α). No re-run is implicated — the ref implementation and every logged number are already on the correct convention.
